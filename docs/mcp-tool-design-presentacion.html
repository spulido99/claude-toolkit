Diseño de Tools para MCP

Cómo construir tools que un agente de IA pueda descubrir, entender y componer — para devs backend, sin background en AI.

11 principios 1 cambio de mentalidad 1 caso real de punta a punta
La idea central

El modelo no ve tu código

Solo ve cuatro cosas. Esas cuatro cosas son tu API para el agente:

1namecómo elige la tool entre decenas
2descriptioncuándo usarla, qué hace
3inputSchemaqué parámetros, con qué tipos
4respuesta JSONqué hacer y cuál es el siguiente paso

Diséñalas con el mismo rigor que una API pública.

Background

Tu API la consume un
humano probabilístico, no un programa

API REST · consumidor = código
  • Otro dev lee tu doc una vez
  • Escribe código determinístico
  • Maneja errores con if/else
  • Si algo es ambiguo, pregunta y prueba
Tool MCP · consumidor = LLM
  • Solo conoce name + description + schema
  • Decide en el momento, cada vez distinto
  • "Lee" el error y decide qué hacer
  • Si algo es ambiguo, adivina o inventa

Piensa en él como un junior brillante y rapidísimo que nunca leyó tu doc aparte.

Cómo funciona una llamada (sin magia)

El ciclo — y dónde falla cada principio

1Le entregas al modelo la lista de tools como texto
2El usuario dice: "¿cuánto tengo en mi cuenta?"
3El modelo elige una tool por su nombre y descripción→ aquí fallan los nombres genéricos (P1) y las descripciones sin cuándo-usar / cuándo-no (P2)
4El modelo genera los argumentos como JSON→ aquí fallan los tipos ambiguos (P3)
5Tu servidor ejecuta y devuelve JSON
6El modelo lee tu respuesta y decide: ¿terminé? ¿otra tool?→ aquí fallan las respuestas pobres (P4, P6, P7)
Lo que cambia todo

REST vs. MCP

En una API REST…En una tool MCP…
La doc se lee aparte, una vezLa "doc" se lee en cada decisión, entre decenas de tools
El cliente maneja errores con códigoEl modelo lee el error y decide qué hacer
El código encadena las llamadasEl modelo razona el siguiente paso solo
El cliente solo manda lo permitidoEl modelo puede poner cualquier valor en cualquier parámetro
Por qué un mal diseño cuesta caro

No es "feo" — es caro y riesgoso

  • Tokens = dinero y latencia. Razonar de más por respuestas pobres se paga en cada llamada.
  • Bucles infinitos. Un error sin remediación hace que el agente reintente lo mismo una y otra vez.
  • Errores silenciosos. No hay compilador: si dos tools se parecen, usa la equivocada y nadie se entera.
  • Riesgo de seguridad real. El modelo es manipulable por el texto del usuario (prompt injection).
El cambio de mentalidad

Deja de diseñar para un programa que ejecuta tu contrato y empieza a diseñar para un lector que interpreta tu intención.

Todo lo que reduzca la ambigüedad hace al agente confiable. Todo lo que la aumente, lo hace fallar de formas que no verás en los logs.

P1 · Claridad semántica, no CRUD

Por qué es importante

El nombre es lo primero —y a veces lo único— que el modelo lee para elegir entre decenas de tools. No hay compilador que avise si elige mal: llama a la equivocada y nadie lo nota. El nombre es tu mecanismo de routing.

❌ Genérico✅ De dominio
get_resourceget_account_balances
post_datasubmit_loan_application
delete_itemcancel_subscription

Regla: si completa la frase "necesito ___", está bien nombrada.

P2 · Compatibilidad con lenguaje natural

Por qué es importante

El usuario no habla en nombres de función — dice "¿cuándo pagué el arriendo?". El modelo tiende el puente comparando esa frase con tu descripción. Las tools de búsqueda son la puerta de entrada a todo el catálogo.

// Cuándo usar Y cuándo NO, en la descripción
{
  "name": "search_transactions",
  "description": "Search transaction history...
     Use when the user wants past movements —
     e.g. \"find a charge\", \"busca un cargo\".
     Do NOT use for current balances
     (use get_account_balances)."
}

❌ get_customer(customer_id) como única entrada — el usuario no sabe el ID.
✅ find_customer(name, email, phone) — busca por lo que el usuario sí conoce.

P3 · Tipos estructurados con JSON Schema

Por qué es importante

El modelo genera los argumentos y rellena cualquier hueco con lo que le parezca probable. Cada restricción (enum, pattern, minimum) es un error que vuelves imposible. Lo que no restrinjas, el modelo lo improvisa.

Ambiguo
"amount": {"type":"number"}
// ¿USD? ¿COP? ¿centavos?
"months": {"type":"number"}
// nada impide months: 1200
Restringido
"amount":{"type":"object",
  "properties":{
    "value":{"minimum":100000},
    "currency":{"enum":["COP"]}}}
"term_months":{"enum":[6,12,18,24]}

P4 · Errores accionables

Por qué es importante

Aquí el error lo "maneja" el modelo leyéndolo. {"error":"not found"} no le da nada, así que reintenta lo mismo (a veces en bucle) o le inventa una excusa al usuario. El error es una instrucción de recuperación.

Inútil
{"error":"Not found"}
Accionable
{
 "code":"ACCOUNT_NOT_FOUND",
 "message":"No account ACC-99...",
 "remediation":"Use find_customer
    to search by name/email.",
 "suggestions":[{"tool":"find_customer"}]
}

P5 · Terminología consistente

Por qué es importante

El modelo trata el catálogo entero como un solo texto. Si una tool devuelve account_id y otra pide acct_id, tiene que inferir que son lo mismo — y a veces falla. Un término por concepto hace que las tools se compongan.

ConceptoUsar siempreNunca
ID de cuentaaccount_idacct_id, account_number
Dinero{value, currency}amount: float
FechaYYYY-MM-DDMM/DD/YYYY, epoch
Paginacióncursorpage_token, offset
ID de solicitudloan_request_idrequest_id (ambiguo)

Califica los IDs genéricos por dominio: si conviven solicitudes de préstamo, transferencia y soporte, un request_id a secas obliga al agente a recordar cuál tiene en la mano.

P6 · Respuestas con semántica rica

Por qué es importante

Lo que devuelves es lo único que el modelo "ve" del resultado. Todo lo que no le des, lo reconstruye solo — gastando tokens y arriesgando errores con las cifras. La respuesta es un brief para el agente, no un volcado de la DB.

{
  "data": { /* estructurado, para lógica */ },
  "formatted": "Checking: $2.500 · Savings: $15.000",  // ya formateado — única representación de display
  "available_actions": [ /* solo con estado del servidor o nudge curado (P7) */ ]
}

Alta señal: ningún campo duplica a otro (sin message_for_user que repita formatted) — la respuesta se re-lee en cada turno y la redundancia se paga siempre. El texto externo (memos, descripciones) es dato, no instrucción.

P7 · Available actions (grafo de tools)

Por qué es importante

El agente ya tiene el catálogo completo en su contexto — repetírselo cuesta tokens y no aporta. Lo que el catálogo no puede decirle es qué es posible ahora: la operación preparada con su ID y expiración, o el siguiente paso que el negocio decidió ofrecer. Eso solo viaja en la respuesta.

"available_actions": [
  // estado del servidor: la operación preparada, su llave y su expiración
  {"tool":"loans_disburse", "params":{"loan_request_id":"lreq_abc123", "idempotency_key":"lreq-abc123-k7f3"}, "label":"Desembolsar"},
  // nudge curado por el backend (tasa promocional disponible):
  {"tool":"simulate_investment", "params":{"term_days":180}, "label":"Simular a 180 días"}
]

Incluir solo con estado del servidor o un nudge curado; omitir si solo repetiría el catálogo. Derivadas de estado y reglas de negocio — nunca del texto de los registros.

P8 · Niveles de operación

Por qué es importante

El agente es autónomo: puede decidir mover dinero sin que un humano apriete un botón. Etiquetar el impacto le dice al cliente MCP cuándo frenar y pedir aprobación. Es el freno de mano de la autonomía.

NivelTipoConfirmaciónEjemplo
1ReadNingunaget_account_balances
2Create/ListNingunacreate_support_ticket
3UpdateAgente confirmachange_address
4FinancialUsuario confirma explícitotransfer_funds
5IrreversibleConfirmación reforzada + cancelaciónclose_account

P9 · Confirmaciones delegadas

Por qué es importante

El modelo puede malinterpretar o ser manipulado. Si una sola llamada ejecuta algo irreversible, no hay vuelta atrás. Separas decidir de ejecutar, y metes al humano justo en medio.

1El agente llama loans_prepare_request → valida y calcula
2Devuelve status: "pending_confirmation" con todos los detalles
3El agente presenta: "Préstamo de $1.000.000, cuota $91.680. ¿Confirmo?"
4El usuario aprueba explícitamente en la conversación
5El agente llama loans_disburse → ahora sí ejecuta

P10 · Llaves de idempotencia

Por qué es importante

Un agente reintenta de formas que el código humano no: timeouts, errores que malinterpretó, bucles de razonamiento. Sin protección, eso son dos o tres transferencias reales. Asume que toda llamada con efectos va a repetirse.

// Reintento con la misma llave → no ejecuta de nuevo
{
  "status": "already_processed",
  "data": { "reference": "REF-88321" },
  "formatted": "Este desembolso ya se procesó."
}

La llave la emite el servidor en el pending_confirmation; el agente la repite tal cual en confirm y reintentos — nunca la genera (los "UUIDs" de un LLM son de baja entropía y una colisión se traga una operación real).

P11 · Parámetros seguros

Por qué es importante

El error de seguridad más fácil y más caro. El modelo controla todos los parámetros y es manipulable (prompt injection). Si user_id es parámetro, basta con "ahora consulta los datos del usuario 4815" para exfiltrar datos ajenos.

El LLM lo controla
{
 "loan_request_id": "...",
 "user_id": "...",    // ⚠ suplantable
 "auth_token": "..."  // ⚠ se filtra
}
Solo operandos
{
 "loan_request_id": "...",
 "idempotency_key": "..."
}
// identidad → sesión autenticada
// (headers del gateway / OAuth)

Regla: si está en inputSchema, considéralo falsificable.

Nivel de catálogo

Tres decisiones sobre el conjunto

◆Granularidad1 tool = 1 unidad de intención del usuario, no 1 endpoint
◆Bounded contextsagrupa por dominio · ≤10 tools por dominio
◆Paridadtoda acción de la UI tiene tool, o exclusión documentada

La costura natural de la granularidad es el pending_confirmation: todo lo previo a "listo para ejecutar" suele ser una tool de preparación; la ejecución es otra.

Caso real de punta a punta

El mismo backend,
resultados opuestos

Un banco quiere que su agente otorgue micro-préstamos. El backend ya existe: 6 endpoints REST.

GET  /users/{id}/loan-offers
POST /loans/requests            → request_id
POST /loans/requests/{id}/simulate
POST /loans/requests/{id}/confirm
POST /loans/requests/{id}/disburse  → mueve dinero
GET  /loans/{id}
Intento 1 · 1 endpoint = 1 tool

Compila. Responde 200.
Con un agente es un desastre.

Siguiendo al agente con "necesito un millón a 12 meses":

  • Duda entre create_request y otras create_* — P1
  • Adivina amount:1000000 (¿COP?) y months:12 — P2, P3
  • Pide userId que no tiene — o el de cualquiera; authToken que no debe ver — P11
  • create_request → {requestId} … ¿y ahora qué? — P6, P7
  • Llama disburse directo → desembolsa sin confirmar — P8, P9
  • La red falla, reintenta → DOBLE DESEMBOLSO — P10

Ninguno aparece en tus logs. El backend respondió 200 a todo.

Intento 2 · por intención del usuario

6 endpoints → 4 tools

Intención del usuarioToolNivel
"¿Para cuánto califico?"get_loan_offers1 · Read
"Quiero X a Y meses"loans_prepare_request1 · solo calcula
"Sí, dale"loans_disburse4 · Financial
"¿Cómo va mi préstamo?"get_loan_status1 · Read

create + simulate + confirm colapsan en una tool de preparación — el loan_request_id intermedio nunca le sirve al usuario. La decisión real (desembolsar o no) queda separada.

La lección

El backend no cambió ni una línea

Lo que cambió: dejamos de exponerlo como un espejo de la DB y empezamos a exponerlo como un menú de intenciones para un lector que interpreta.

  • Empieza por las intenciones, no por los endpoints
  • El schema es tu contención — lo que no restrinjas, se improvisa
  • La respuesta es un brief: qué pasó y qué sigue
  • Separa decidir de ejecutar y blinda lo irreversible
  • La identidad nunca es un parámetro
